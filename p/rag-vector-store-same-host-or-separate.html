RAG: Should the Vector Store Live on the Model Host?

Same machine is simpler and faster until memory pressure turns your p99 into a random number.

In short

The vector index lives in RAM, the model lives in VRAM — they compete only when the host runs out of system memory. Size the index first, then decide.

Two budgets people confuse

A vector database and a model on the same host do not fight over the same memory. The model occupies GPU memory. The index occupies system memory, unless you deliberately built a GPU index.

So the question is not "do they fit in 24 GB" — it is "does the host have enough RAM for the index plus everything else". Those are different budgets, and conflating them is how people end up renting a bigger GPU to fix a RAM problem.

Sizing the index before deciding anything

Raw vectors are easy: count × dimensions × 4 bytes for fp32. One million 768-dimension vectors is about 3 GB.

The index structure is the part people forget. HNSW keeps a graph alongside the vectors, and the overhead is substantial — plan for roughly 50% on top, more at high M values. That same million vectors is then closer to 4.5 GB resident.

Then add headroom. A vector database being written to while serving reads needs room for both the current graph and the rebuild. Sitting at 85% RAM utilisation is not "fine" — it is the state right before the OOM killer picks a victim, and the victim is usually the process serving traffic.

When same-host is the right call

For a single-tenant service with a modest corpus, co-locating is the better engineering choice. The retrieval call becomes a loopback request instead of a network hop, which removes an entire failure mode: the p99 spike that used to arrive with every network hiccup stops happening.

It is also cheaper and easier to reason about. One machine to monitor, one set of logs, one deploy. At small scale that operational simplicity is worth more than the theoretical isolation you gave up.

When to split them

  • The index needs more RAM than the model host can spare — the common case once you pass a few million vectors.
  • You need to scale retrieval independently. Query load and generation load rarely grow at the same rate.
  • The corpus is shared by several model endpoints. One index serving three services beats three copies of the same index.
  • You rebuild the index regularly and cannot afford the memory spike next to the model process.

Check what the process actually holds

# RSS is what matters -- VIRT includes mapped files that are
# not resident and will make you think headroom is smaller
# than it is.
ps -o pid,rss,vsz,cmd -p $(pgrep -d, -f vector)

# Available, not free. `free` counts page cache as used,
# which makes a healthy host look nearly dead.
free -m | awk 'NR==2 {print "available: " $7 " MB"}'

Common questions

Can I put the vector index on the GPU too?

Yes, and it is fast — but on the same GPU the model already occupies. A GPU index trades VRAM for latency, which is the wrong trade when model memory is your constraint. Use it only for small corpora with tight latency budgets.

Does co-locating hurt retrieval quality?

No. Retrieval quality depends on the embedding model and chunking, not on where the index runs. What changes is failure behaviour under memory pressure.

How much RAM should stay free?

Enough that the index plus CPU-side model buffers stay below 80% of total. Past that you are one concurrent rebuild away from the kernel picking a process to kill — and it does not pick the one you would have.

Decide with four numbers

  • Step 1. Count vectors and multiply by dimensions × 4 bytes.
  • Step 2. Add roughly 50% for the HNSW graph — check your index type's documentation, the overhead varies.
  • Step 3. Compare against the host's available RAM, not total RAM.
  • Step 4. If it exceeds 60% of available, split the deployment; otherwise co-locate and keep the loopback path.
